# FinPilot Benchmark Harness

Every number reported in the project's results chapter is produced by this harness and can be
re-derived from a seed. Nothing here is estimated or hand-written.

## Prerequisites

Benchmarks run against a dedicated local MongoDB, never the development cluster. It is the same
container the test suite uses (`../docker-compose.test.yml`), on port 27018, in a separate database:

```bash
npm run test:services        # docker compose -f docker-compose.test.yml up -d
npm run bench:seed -- --transactions=100000
npm run bench:e2
```

`bench/lib/db.js` refuses to connect to any host that is not `127.0.0.1`/`localhost`, and to any
database not named `finpilot_bench`. The seeder drops the database on every run, so this guard is
load-bearing.

Override with `BENCH_MONGO_URI` if needed (the guard still applies).

## Why a local database

The application's `MONGO_URI` points at a hosted cluster and the cache at Upstash over REST. Network
round-trip variance on a shared cluster is larger than several of the effects being measured, so any
result taken against it would be unreproducible and meaningless. Measurements are taken locally,
where the only variable is the code under test. This is a limitation to state explicitly in the
report: absolute latencies are lower than production would show; the *relative* comparisons are the
finding.

## Seeding

```bash
node bench/seed.js --transactions=100000            # defaults: seed=42, workspaces=3, accounts=6
node bench/seed.js --transactions=1000000 --seed=7
```

Each run writes `bench/results/dataset-<N>.json` — the manifest, containing the exact options,
document counts, storage/index sizes, and load throughput. The manifest is generated by the run and
is the artefact the report cites for its dataset description.

The seeder verifies its inserts against `countDocuments()` before writing a manifest and refuses to
report a partial load. An earlier revision reported "1,000 inserted" into an empty collection —
Mongoose's `insertMany` with `ordered: false` defaults `throwOnValidationError` to false and resolves
successfully even when every document is rejected.

## Dataset description

Deterministic: the same `--seed` and options reproduce the dataset exactly, `_id`s included.
This holds because

- all randomness comes from a single seeded mulberry32 PRNG (`lib/rng.js`),
- `_id`s are derived from that PRNG rather than `ObjectId()`'s clock/counter,
- dates derive from a fixed `REFERENCE_DATE` (2026-07-01T00:00:00Z), never `Date.now()`.

Verified by re-running a seed and comparing an MD5 over all sorted `_id`s.

### Entities

| Entity | Count | Notes |
|---|---|---|
| User | 1 | Owns every workspace; bcrypt hash precomputed (insertMany bypasses the `pre('save')` hash hook) |
| Workspace | `--workspaces` (default 3) | First is `personal`, rest `family` |
| Category | 14 per workspace | 4 income, 10 expense |
| Account | `--accounts` per workspace (default 6) | Opening balance 500,000 so balance updates cannot breach the schema's `min: 0` |
| Transaction | `--transactions` | Round-robin across workspaces, so per-workspace counts stay balanced |

### Transaction distributions

Chosen to approximate a household spend profile. Uniform distributions were rejected: they flatten
index selectivity and make `$group` look cheaper and more predictable than it is in production.

| Property | Distribution |
|---|---|
| Type | 18% income / 82% expense |
| Income categories | Salary 70%, Freelancing 15%, Investments 10%, Interest 5% |
| Expense categories | Food 24%, Transport 14%, Housing 12%, Utilities 10%, Shopping 10%, Entertainment 8%, Health 7%, Education 6%, Travel 5%, Misc 4% |
| Amount | Skewed (`u^2.2`): income 15,000–250,000; expense 50–40,000 |
| Payment method | UPI 40%, credit card 20%, debit card 14%, cash 12%, bank transfer 10%, wallet 4% |
| Merchant | Uniform over a 250-name pool (bounded cardinality gives `merchant.name` realistic selectivity) |
| Status | 4% `pending`, else `completed` |
| Soft-deleted | 2% (so `isDeleted: false` filters do real work) |
| Date | Uniform over 24 months preceding `REFERENCE_DATE` |

`status` and `isDeleted` are drawn independently; sharing one draw would correlate them and make
"pending AND deleted" impossible.

### Verified at N=1,000 (seed 42)

| Property | Observed | Target |
|---|---|---|
| Income share | 0.158 | 0.180 |
| Soft-deleted share | 0.014 | 0.020 |
| Pending share | 0.030 | 0.040 |
| Distinct merchants | 243 | ≤250 |
| Per-workspace counts | 333 / 334 / 333 | balanced |
| Date range | 2024-07-11 → 2026-06-30 | 24 months to 2026-07-01 |

Deviations are sampling noise at n=1,000 and converge at larger N.

## Indexes

`autoIndex` is disabled on the benchmark connection. Indexes are built explicitly *after* the load,
via `syncIndexes()`, because building during insert both slows the load and conflates index-build
cost with query cost. The index/no-index experiment drops and rebuilds them deliberately.
